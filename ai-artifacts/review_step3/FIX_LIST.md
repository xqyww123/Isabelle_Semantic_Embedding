## D11-revised review: rulings (all 'fix')

### [blocker] The `_GATING` early return still writes a text under a verdict computed for a different text — the premise the user just overruled, surviving in the branch the note did not revisit

All three lenses raise this (soundness F1, concurrency F1, elegance F1) and I rule them together; it is the one thing that is unsound as the note is written. The note's argument is 'the gate compares interpretation TEXTS, so a correction changes the fresh text and the verdict can change' — and it draws the conclusion only for the `_DONE` edge. For `_GATING` it keeps the old rule verbatim ('the running gate writes the newest text'), which is the same refuted reasoning. Verified on the plan and the code: §15.5's `_gate` passes `task.results[key]` to `_prefilter` and to `_judge`, and `_write` re-reads it independently (`text = task.results[key]`, plan §15.5; on disk semantic_interpretation.py:885). From step 5 there are two awaits in between — the prefilter, bounded by `_PREFILTER_TIMEOUT_S` = 60 s, and the judge session, measured by D3 at 8-10 s (Claude Code) / 13-20 s (Codex) plus any wait for one of D12's 40 permits. I measured the mechanism on this interpreter with a judge that awaits and a correction landing mid-await: 'judged: [T1] | written: [(T2, same)]' as the note has it, versus 'judged: [T1, T2] | written: [(T2, different)]' with the fixpoint. When the superseded verdict is UNCHANGED the store keeps T2 with the version unmoved, the baseline unmoved and no propagation, and since the entity's `semantic_digest` did not change it is neither locally stale nor a seed of any future scan — the meaning change is lost permanently. D2 names that as the outcome to avoid. The window is not contrived: the batch-complete reply ('If you noticed any mistakes in your translations, correct them now', :761-766) fires exactly when the batch's last gates have begun judging. I also confirmed the branch is reachable today: driving the on-disk `InterpretationTask` with a stubbed `start_gate`, a second `on_answer` for the same index while the state is `_GATING` replaces `results` and starts nothing (harmless in step 3, where the gate body has no await). Blocker, not major: leaving it would write the overruled premise into the plan, and the failure it produces is silent and irreversible.

**Fix:** Make 'the text written is the text the verdict was computed from' structural, by re-running the gate rather than letting `on_answer` substitute a text under a finished verdict. In §15.5's `_gate`: capture the record and the text at the top of each round, judge THAT text, and immediately before the write — with no await between the test and the write, so the value cannot move under it — compare and start over if it moved:

    async def _gate(task, idx):
        e = task.entries[idx]
        while True:
            rec = task.rec_cache[e.universal_key]     # the record as currently stored (item 3)
            text = task.results[idx]                  # the text this round judges
            verdict = ... prefilter / judge over `text` ...
            if task.results[idx] != text:             # a correction landed mid-gate
                continue                              # judge the new text; nothing written, nothing minted
            minted = _write(task, idx, rec, verdict, text)
            break
        if minted:
            _propagate(task, idx)

`_write` takes the judged text (and the record) as parameters and drops its own `text = task.results[key]` re-read. `on_answer` keeps the note's shape exactly; its `_GATING` early return becomes a true statement ('a gate is running; it will pick this text up AND judge it') instead of the old D11 rule under a new name. Termination: every extra round is paid for by one distinct correction, and corrections are finite per run; in a gate with no await (step 3) the loop always runs exactly once. Two consequences worth keeping: the store then agrees with `task.results`, which is what `interpret_file` returns to Isabelle (:1458-1461) — without the loop the two can disagree; and the note's open question about two corrections in quick succession on a `_DONE` entity stops being a special case, because the running gate simply notices the text moved. Staging: land the `_write(…, text)` signature in step 3 (it cannot change behaviour there — no await inside the gate) and the loop in step 5 with the awaits that make it reachable; §15.5's block shows the step-5 shape.

### [major] `n_interpreted` cannot be corrected at the site the note names: at `_write` a first gate and a re-gate are both `_GATING`

Concurrency lens F2, and elegance F3's tail. The note already commits to the right RULE ('counts entities, not gate runs: increment only when an entity first reaches `_DONE`'), but the only place the increment lives is `_write` (semantic_interpretation.py:904-905; plan §15.5 'task.state[idx] = _DONE; task.n_interpreted += 1'), and there `task.state[idx]` is `_GATING` on a first gate and on a correction's gate alike, because `on_answer` sets `_GATING` before `start_gate` on both paths. So the rule as stated cannot be transcribed at that site, and a literal transcription over-reports: the host log at :1417 prints a count above `enrolled()` and the approved closing line §12 #7 ('<A> entities interpreted') reports more entities than the theory has. I checked both readers — :1417 and :1451 are the only ones, and both run after the task group has joined, at which point :1439 already asserts every entry is `_DONE` or `_NOT_ENROLLED`. So a derived count is exactly today's number on every run without a correction, and the right one with corrections. Major rather than minor because it silently falsifies an approved user-visible line and the step-3 acceptance bullet, and because the note's own rule is unimplementable where it points.

**Fix:** Do not count, derive — the idiom `AgentTask` already uses for every other run-wide number (`enrolled()` :424, `answered()` :428). Add beside them:

    def n_interpreted(self) -> int:
        """A of §12 #7: the entities this run wrote — counted once however
        many gates each needed (D11)."""
        return sum(1 for s in self.state if s == _DONE)

Delete the field at :561 and the increment at :905; the two readers become `task.n_interpreted()`. Double counting is then unwritable rather than something to remember. F6's prescribed store-backed test asserts `task.n_interpreted == 2`; it becomes `task.n_interpreted() == 2`.

### [major] The gate's record must be ONE `rec_cache` lookup per gate handed to `_write`, and `task.recs` must leave the task with it — the pre-run record does not merely show a stale baseline, it rolls a committed mint back

Soundness F2, concurrency F3, elegance F4, ruled together. The note's rule (read `task.rec_cache[uk]`) is right and necessary, but its stated reason ('or the second gate would see the pre-run baseline') names the smaller half, and the plan is only half-switched by changing the one line the note quotes. §15.5 shows `rec = task.recs[idx]` once, but `rec` has TWO consumers: the judge decision in `_gate`, and three separate uses in `_write` (the first-write test `rec is None or rec.semantic_digest is None`; the not-judged row's `rec.version … else w.counter_value()`; and the UNCHANGED branch's `version, baseline = rec.version, rec.baseline_interpretation`). `_write` is printed as its own function and on disk already reads its inputs from the task (:884-885), so a second, independent read is the natural transcription. With the pre-run record, a correction whose first gate minted and PROPAGATED and whose second verdict is UNCHANGED writes back the pre-run version and the pre-run baseline: the entity's version drops from the minted value to the pre-run one, its `interpreted_at` recomputes below the mint, and every dependent that mint enrolled or snapshot-raised reads back as not stale — a committed, already-propagated mint erased, which breaks version monotonicity outright. The pre-run record is wrong in the not-judged rows too: a theorem-alike entry whose first gate took ε = `counter_value()` would re-take a counter that another entity's mint may have advanced, so its version drifts upward for no reason. `rec_cache` is right in both cases by construction: it is populated for every entry at the scan (§15.8 item 1) and written back from inside every gate transaction (§15.5), so it is the pre-run record for a first gate and the first gate's record for a re-gate. After the switch nothing reads `task.recs` at all, yet §15.3 declares it and §15.8 item 7 fills it — a second, staler record map whose only possible use is the wrong one.

**Fix:** Read the record once per gate and hand it on: `rec = task.rec_cache[e.universal_key]` at the top of each round of `_gate` (item 1's loop), `_write(task, idx, rec, verdict, text)`; `_write` never looks a record up for itself. Then delete the `recs=` parameter and `self.recs` from §15.3's constructor and `recs=recs` from §15.8 item 7: `recs` stays a local of the scan, which needs it to build `rec_cache` and to decide local staleness. With no pre-run record on the task, no later author can read one. `_EffStar` needs no change: a fresh instance per gate call over `rec_cache` is already prescribed, and that is exactly what a second gate needs — a shared memo built before the first gate's mint would be stale for the second.

### [major] The `rec_cache` switch silently redefines §3's R, and the plan must say what a correction of an entity this run first wrote does (it is judged, and may mint)

Soundness F3 and elegance F2 raise this; I accept the defect and REJECT the remedy both propose. The defect: §3's preamble reads 'with R the record as stored before this run (R may be absent)', and every row is decided from R. Item 3's switch makes R the CURRENT record, which the note never says. Left as is, the implementer must guess, and the natural guess ('R is the pre-run record, as §3 says') reintroduces exactly the rollback of item 3. So the preamble must be rewritten, and the consequence stated: after a first gate the record has a digest and a baseline, so §3 row 1 (`rec is None or rec.semantic_digest is None`) is no longer reachable for that entity and its correction takes the judged rows — one judge session, and on CHANGED a mint that propagates. The remedy both lenses offer — keep row 1 'sticky' by deciding it from the pre-run record — I reject. It reintroduces per-entry pre-run state on the task that item 3 has just deleted (a list of booleans is still pre-run state), and it makes the row depend on history, which is precisely what the note's uniform procedure is built to avoid ('both histories are handled by the one procedure without inspecting the previous verdict'). The cost it prevents is smaller than claimed, and I checked why: in a first interpretation of a theory every entity is a seed, so every dependent is already enrolled and `_propagate` finds no `_NOT_ENROLLED` one to re-interpret — the mint costs a judge session plus a few snapshot raises, not LLM work. Where a dependent IS `_NOT_ENROLLED`, the first write's ε (= `counter_value()`, the current counter) would in most cases have made it stale on the next run anyway, so the mint mostly pulls that work forward. And nothing consumed the superseded first text: §15.8's addressing rule has `mk_query_by_name_tool` refuse every enrolled name, so no dependent's English in this run was informed by it. That leaves needless propagation, which D2 licenses in as many words. Major because the plan-text contradiction is load-bearing and a wrong resolution costs data integrity.

**Fix:** (a) §3 preamble: R is the record as it stands when THIS gate runs — `task.rec_cache[E.universal_key]` — i.e. the record before this run for a first gate and the record the previous gate wrote for a correction's gate. (b) Add one paragraph after §3's table stating the two consequences for a correction: an entity first written this run takes the judged rows on its correction, and a CHANGED verdict there mints — deliberate over-signalling under D2, not a defect; and a not-judged row (theorem-alike, WIP collection/method, persistent) re-runs unchanged, taking its version from R, so a second write keeps the ε its first write committed instead of re-reading a counter that may have risen. Do NOT add a pre-run boolean, a fifth row, or any other per-entity memory of the first gate.

### [minor] A byte-identical resubmission should start nothing: as written it buys a second judge session, whose nondeterminism can mint and enrol dependents for a text that did not change

Concurrency F4. Nothing in the note tests whether a correction actually changes the text, and the batch-complete reply actively solicits resubmissions, which agents do sometimes take literally by re-sending a whole batch. The certain cost is one LMDB write plus a tombstoned vector per resubmission — `put_interpretation`'s first act is `invalidate_vectors([key])` (semantics.py:990) — which a later `_auto_embed` must pay to re-embed. From step 5 the real cost is a judge session (D3: 8-20 s, ≈$0.13) on a pair the judge has already seen, and that is where it stops being merely wasteful: judge sessions are independent LLM sessions and are not deterministic (§1 quotes a measured 0.8 % false-alarm rate), so a verbatim re-send of a text whose first verdict was UNCHANGED can come back CHANGED, mint a version and enrol not-yet-enrolled dependents for full LLM re-interpretation — for a text that provably did not change. One line makes that unreachable, and it is exact in every state, which I checked: `results[idx]` is None for a queued or sent entry (so the answer path is untouched), it is the text the store holds when the state is `_DONE`, and the text the running gate will write when the state is `_GATING`. Minor, and it composes with item 1: real corrections still re-gate, and the cost of corrections scales with real corrections by construction.

**Fix:** At the top of `on_answer`, above the state tests:

    old, self.results[idx] = self.results[idx], text   # in memory only (D14)
    if text == old:            # a resubmission that changes nothing changes nothing:
        return                 # no second gate, no judge session, no vector tombstone

The rest of the note's block follows unchanged. Add a §10/§15.10 case: a byte-identical resubmission of a `_DONE` entity starts no gate and leaves the record byte-identical.

## D11-revised review: open questions settled

**1. Concurrency of two gates on one entity — is the note's claim sound?**

The conclusion is right; the warrant the note gives is not the one that holds. The note says "`_DONE` is set at the end of the first gate's synchronous write, and `gate_finished` follows". The second half stops being true once F4's shape (which the note keeps) is applied: F4 pairs the counter's decrement to the task with `add_done_callback`, and a done callback runs one `loop.call_soon` AFTER the task itself has finished. I measured this on this interpreter (CPython 3.12.3): after one `await asyncio.sleep(0)` the task reports `done() == True` while the counter still reads 1; it falls to 0 on the following pass. That is harmless — the counter can only read too high, which is the safe direction for a termination test, and the same callback sets `_progress`, so a parked loop wakes and then reads the decremented value — but the plan must not rest on it.

The warrant that does hold: `_write` sets `task.state[idx] = _DONE` as its last statement, and there is no `await` between that and the gate coroutine's return — `_propagate`'s `gate_write()` transactions are synchronous context managers. Since `on_answer` runs synchronously inside the `answer` tool handler on the same single-threaded loop, any handler that OBSERVES `_DONE` is running strictly after the first gate coroutine finished, propagation included. So two gates for one entity can never overlap. Write that warrant into §5.4/§15.5, because it is fragile in a specific way: if step 5 ever moves the blocking LMDB write onto a thread (`asyncio.to_thread`) or awaits anything inside `_propagate`, two gates on one entity become genuinely concurrent and both write.

Can the queue loop observe `gates_running == 0` while a correction's gate has just been created? No, twice over. The increment precedes `create_task` (F4's ordering), so the counter never dips below the number of gates that exist; and a correction can only arrive inside the `answer` tool handler, i.e. inside `driver.run_turn`, while `_run_agent` is awaiting that turn — the loop's `if not task.gates_running: break` (:995) is not reached until `run_turn` has returned. I also confirmed there is no missed-wakeup hole in the other direction: the loop parks in `wait_for_progress()` only when the batch is empty, and while it is parked no turn is in flight, so no tool call and therefore no correction can arrive during the park.

Two corrections in quick succession on a `_DONE` entity: the first flips `_DONE → _GATING` and starts gate 2; the second sees `_GATING` and only replaces the text. As the note writes it that is **not** sound — it is finding 1 one level down: gate 2 judges the first correction's text and writes the second's. With item 1's fixpoint it becomes sound and stops being a special case: the gate simply notices the text moved and judges again.

**2. Second gate + propagation — is anything double-counted, and does the queue still terminate?**

Nothing is double-counted, and I could not construct an unsound case. Three reasons, each checkable from the plan's own text. (a) `interpreted_at` is a snapshot recomputed from `rec_cache` at each write, never an accumulator, and `eff*` is a maximum, so a repeated snapshot raise is idempotent up to the higher value. (b) Every gate write puts its record back into `rec_cache` from inside the transaction (§15.5), and a gate builds a FRESH `_EffStar` per call, so a second gate reads a cache that equals the store — including a mint made between the two gates. (c) Every one of §5.3.1's three propagation actions is re-runnable: a `_NOT_ENROLLED` dependent is enrolled at most once (`enqueue` moves it to `_QUEUED` immediately, so the queue receives at most n items over the whole run), a `_QUEUED`/`_SENT`/`_GATING` one is passed over and its own later write recomputes `eff*` from scratch, and a `_DONE` one is raised again to a value that is ≥ the previous one by construction.

A double mint therefore harms nothing: versions only rise (I1 intact), the counter is not scarce, and the second mint re-signals to a dependent set the first already covered. The only real cost is the second judge session, and the only silly sub-case is a correction that reverts the meaning to what the store already held — over-signalling, which D2 accepts in as many words.

I also checked the two orderings that could interleave badly and neither can: the writes are synchronous, so either a dependent's own write happens first (and the propagation then finds it `_DONE` and raises it) or the propagation happens first (and the dependent's own write picks the mint up from `rec_cache`). There is no third interleaving.

Termination is unaffected. Gates are started only from `on_answer`, which runs only inside a tool call inside `run_turn`, so between turns `gates_running` only falls; enrolment is bounded by the `_NOT_ENROLLED` guard; and a written entity is never re-interpreted, only snapshot-raised, so there is no enrol-mint-enrol cycle. Item 1's inner loop adds at most one round per distinct correction, which is finite because corrections are agent-initiated. One plan sentence does need widening: §5.2's "Why the run is bounded" counts interpretations and mints per entity; gate runs and mints are now bounded by the number of SUBMISSIONS, not by the entity count. Nothing diverges, but the bound should say what it rests on.

§14's invariant survives untouched — "every stale entity is either a seed or enrolled by the mint that made it stale" does not depend on how many verdicts an entity receives, only on every mint propagating before its gate returns and on `interpret_file` joining the group before it returns, both of which still hold. §14's parenthesis about a second verdict not existing is what breaks (item 6).

**3. `rec_cache` as the gate's record source — enough, and does it touch `_EffStar`?**

Yes, and it is required, not merely sufficient — see item 3 for the failure the note's stated reason does not cover (a second UNCHANGED verdict writing back a version a mint of this run already superseded). Two conditions on top of the note's rule: it must be ONE lookup per gate handed to `_write`, because `rec` has consumers in both functions and a half-applied switch leaves the second one reading the pre-run record; and `task.recs` must leave `InterpretationTask` entirely, so the wrong record is unreachable rather than merely unused. `_EffStar` needs no change at all: "a fresh instance per gate call over `rec_cache`" is already prescribed and is exactly what a second gate requires, since its memo is per-instance and a mint between the two gates would be invisible to a shared one. And §3's preamble must be rewritten to match (item 4).

**4. Deleting `update_interpretation` — any other consumer?**

None, present or planned; I verified this rather than taking it on trust. `grep -rn "update_interpretation"` over the whole MLML tree returns: `semantics.py:789` (the definition), `semantic_interpretation.py:580` (the one production caller — the `_DONE` branch being deleted), five tests in `archive/tests/test_semantic_change_gate_storage.py` (lines 3, 84, 137-190), the plan/handoff/review documents, and — outside this project — only `update_interpretations`, plural, which is the unrelated policy shell at `semantics.py:1858`. Nothing in steps 4-8 wants a text-only write that preserves gate fields: the statement refresh uses `update_expr` (§5.3.2, §15.8 item 8), the snapshot raise uses `update_gate_fields` (§15.5 `_propagate`). `_put_fields(create=True)` keeps a user in `put_interpretation`, so no dead code is left behind in `semantics.py`.

Deleting it takes with it: the four `update_interpretation` tests (:137-190), the storage-test module docstring's "two field-disjoint entry points `update_interpretation` and `gate_write`" (line 3), and `ai-artifacts/SEMANTIC_CHANGE_GATE_HANDOFF.md:18`. One piece of coverage is not duplicated elsewhere and is worth one line to keep: those tests carry the legacy-arity parametrisation `n ∈ {12,13,14,15}` on the INTERPRETATION write path, while `test_gate_write_on_a_legacy_arity_record` (:211-223) covers only `update_gate_fields`. Both go through the same `_put_fields`, so this is cheap insurance rather than a real gap — carry the `@pytest.mark.parametrize` onto §15.10's new `put_interpretation` test. `update_interpretation`'s docstring sentence about crash shape (i) needs no new home: with exactly one interpretation writer, "an answer that lands and a gate that never runs leave nothing on disk" is guaranteed by there being no other writer, which is the stronger statement §6.4 already makes.

**5. The step-3 acceptance bullet (§15.11).**

The proposed wording is accurate but short by two clauses, and it is only true once item 2 lands. In step 3 the correction re-runs `_write` with the same `inv_fields` pair, so the bytes written are what `update_interpretation` wrote plus the same gate fields the first write already put there — genuinely no observable difference in the record. But `_write` increments `n_interpreted` unconditionally (:905), so without item 2 a corrected entity is counted twice and the closing line reports more entities than the theory has; and the correction's write moves out of the tool handler into the gate task, so on the success path it is no longer synchronous with the tool reply (it lands at the handler's next await, `await _report(...)`, still before the reply reaches the agent) and on the failure path it fails the RUN, where today it escapes the handler as an opaque MCP `isError`, is reported to the agent, and the run still succeeds. Suggested wording is in plan_edits.

**6. Elegance; §5.3.1 and §14; does "correction" need a name in the code?**

The shape is not a hack — it is a strict improvement on what it replaces, and I would defend it on elegance alone. It removes the one write in the system that had no verdict behind it, so "every interpretation write goes through `gate_write`" becomes structural instead of remembered; §6.4 shrinks from two entry points to one; D14 becomes exact; yesterday's whole P2 apparatus (a separate write task, `start_write`, `_correct`, `writes_running`, a new glossary row, a third crash shape) is deleted rather than reviewed, and `gates_running` / `start_gate` stay honest because everything the task group carries really is a gate again. No new glossary row is needed, and "correction" needs no name in the code: after the change it is one state machine with one new edge, and the comment on that edge should say what the edge IS ("an answer for an entity already written: gate it again — the verdict compares texts, and the text changed"), not name a category.
